# 人工评审规则重设计

> 设计版本：v1（2026-10-24）
> 设计审查：PASS；模式：independent；轮次：2/3
> 设计确认：已确认 v1；依据：用户在设计交付后回复“实施”。实施不包含未经授权的历史任务合并。
> 本文替代的是旧版风险升级与人工分流策略；实施前仍执行现行规则。本文件不维护实施进度。

## 1. 问题与目标

当前把模型 risk=high、400 行/10 文件门槛、契约版本变化、评审基础设施失败等汇入“高风险→人工”。它回答的是“改动是否值得注意”，没有回答“为什么必须由人处理”。

真实案例：#39 并发执行有可复现的错误吞噬，应让编码 Agent 修复；#40 新增可选 CLI 参数且旧默认不变，应由兼容性证据决定；#41 是 409 行代码抽取，应评估行为与解决冲突，而非因为多 9 行交给人。已关闭的 #26/#82 应退出当前待处理。

目标：AI 自主完成需求实现、补证、修复、评审和落地；人工只处理明确决策、授权或人工模式交接。失败必须可见，但不伪装成代码高风险。

非目标：保证 AI 零漏报；增加 reviewer shell 权限；让外部裸 PR 自动修复/合并；自动重开关闭任务；实现新项目管理系统。

## 2. 四个问题独立判断

| 维度 | 判定 | 不得推导的结论 |
|---|---|---|
| 正确性 | 需求是否满足，有无确定性缺陷 | 测试通过≠没有缺陷；缺陷≠需要人修 |
| 证据 | 关键行为是否已验证，是否存在具体缺口 | 缺测试框架≠代码高风险；没有记录≠测试通过 |
| 授权与兼容 | 是否超出已批准目标，是否需要选择方案/额外授权 | 改契约版本号、新增文件、依赖文件被触及≠必须人工 |
| 执行健康 | 模型、GitHub、检查环境、现场和协议是否可靠 | 网络超时、格式错误、预算耗尽≠业务风险 |

主判定不再依赖 low/high 二值。规模、路径、模型的风险提示用于选择核查重点和资源预算，不能单独决定人工交接；项目显式配置的人工保护路径属于例外，是用户选择的授权门禁。

## 3. 分流顺序与终点

顺序不能由各阶段临时覆盖：

1. 核对当前任务/PR/Issue、人工锁、取消、模式、HEAD 和现场完整性。外部已关闭先对账，暂停/人工模式不越过。
2. 查确定性保护门禁和额外授权；已有明确人类决定优先，reviewer 无权扩大授权。
3. 宿主按已审 SHA 收集完整 diff 和适用检查证据；缺失或不可靠先恢复，不写可合并 PASS。
4. 独立 reviewer 审查，给出缺陷、具体补证请求、决策请求或放行依据。
5. 宿主验证输出并执行下表；先处理不能自动落地的决策门禁和不可靠证据，再处理确定性缺陷。修复可继续在授权范围内做，但不清除已有决策门禁。
6. 只有完整评审、证据闭合、无未解决缺陷、无授权门禁时才进入 MERGING；落地前再次检查 SHA、base、生成物、检查和远端保护。

| 结果 | AI 动作 | 展示/状态 |
|---|---|---|
| 可验证的代码缺陷 | 通过现有 pending_fix 派修复；补回归测试；新 HEAD 重新检查、评审 | 自动修复中；沿用 DISCOVERED/运行相位 |
| 具体证据缺口 | 已有检查由宿主补跑；缺场景则派编码 Agent 补最小回归测试，再完整评审 | 补充验证中；不是人工评审 |
| 临时执行失败 | 有界退避重试，复用未变 HEAD 的有效证据 | AWAITING_REVIEW + 可见下次重试时间 |
| 执行持续失败/修复预算耗尽 | 停止循环，保留现场与证据，给出恢复动作 | BLOCKED/RECOVERY_REQUIRED，“执行受阻” |
| 明确人类决策/额外授权/显式保护 | 等待回答具体问题，禁止自动落地 | AWAITING_HUMAN，“待你决策” |
| 评审与证据闭合 | 自动落地策略开启则 MERGING，否则等待配置要求的合并批准 | 配置交接显示“等待合并批准”，不是高风险 |
| 裸 PR | 只给建议，仍不运行项目检查、派修复或合并 | 依现有 advisory 路径，明确“外部 PR 评审完成” |

“执行受阻”仍可能需要维护者操作，但不能出现在“待你决策”数量里；它属于同一看板的故障视图，不新增另一套任务系统。

## 4. 哪些情况需要人

### 4.1 必须人工

- 存在相互冲突的需求或两个不可兼容方案，已批准需求不能确定取舍。
- 新增不可逆生产删除/迁移、权限扩大、认证/密钥/发布信任边界变化；即使 Issue 宽泛写“优化”，也不等于有具体执行授权。首次发布此策略不允许自动略过这些门禁。
- 未经批准的破坏性兼容变化，且无法在目标内改成兼容实现。
- 项目 review_mode=manual、auto_merge.enabled=false、人工锁或显式人工保护路径。这是用户工作流选择，不声称代码危险。
- 宿主发现 reviewer 现场被篡改或恢复进程身份不确定，进入安全/恢复受阻；禁止提供普通“批准忽略”来绕过完整性校验。

授权只接受任务已持久化的需求/人类批准记录，不接受 reviewer 自述“已获同意”。权限、密钥等首次策略保留显式人工审批，即使实现被需求提及也必须产生具体批准记录。

### 4.2 默认由 AI 完成

| 变化 | 要求的依据 | 不再采用的旧规则 |
|---|---|---|
| 新增可选参数/字段、默认行为不变 | 参数校验、旧调用回归、新行为验证、契约与生成物一致 | 仅 contractVersion 变化即 high |
| 需求明确的普通行为变化 | 新行为符合验收、原受影响路径回归；破坏性变更另走人工授权 | 一切公共 API 变化均 high |
| 重构/文件移动/抽取 | 调用方检查、行为回归、构建验证；移动量只用于分段 | 400 行或 10 文件即人工 |
| 测试、测试脚本、文档与生成物 | 测试非空且不弱化覆盖；生成物由已审源码重建 | 改 tests/package.json 即 high |
| 普通依赖调整 | 符合任务范围、安装与构建成功、版本/锁文件一致；涉及供应链执行/凭据变化时明确门禁 | 所有依赖变更自动人工 |
| 合并冲突 | 宿主 fetch、编码 Agent 修、完整检查和新 HEAD 重新评审 | 直接交人，或继承旧 SHA 批准 |
| 测试失败、确定性 Bug | 在预算内自动修复，不为通过而删断言/降级检查 | 把 BLOCK 当成人工评审请求 |

对代码行为变化，所需证据可以是聚焦回归、契约验证或可重复探针，不强制每次跑所有测试。纯文档/注释可由静态核对闭合；关键运行行为无法验证时保持证据缺口，不自动放行。

## 5. reviewer 的新输出与宿主职责

输出协议 v2（示意）：

```json
{
  "protocol_version": 2,
  "summary": "结论说明",
  "findings": [{"file":"src/cli.js","line":715,"trigger":"插件 Promise.reject()","impact":"并发退出 0，CI 假绿","verification":"比较 concurrency=1/2 退出码"}],
  "verification_requests": [],
  "decision_requests": [],
  "compatibility": {"kind":"additive","evidence":["旧默认路径回归通过"]}
}
```

- findings 必须包含位置、触发条件、影响、验证方法；推测只能形成 verification_request，不能冒充确定性缺陷。
- verification_request 必须写清待验证的命题、场景与成功标准；“缺测试”“无法排除回归”不构成有效请求。
- decision_request 必须包含具体问题、可选方案、影响、为什么已有授权不能决定；引用位置或需求冲突。宿主不接受仅“契约变更/文件过多/模型 high”等理由作为人工门禁。
- compatibility 枚举：unchanged/additive/breaking/unknown。unknown 不直接变成人工请求：先核查调用方/补证；确实存在产品取舍才进入决策。
- 对运行行为改动提交“正常路径、错误路径、输入边界、旧调用兼容”的覆盖说明；每项引用实际证据或说明不适用。并发/异步错误处理尤其验证非 Error 拒绝值、退出码、在途收尾；不能因基线测试全绿跳过新增分支检查。
- 是否放行由宿主根据有效结构化输出、门禁、检查、SHA 和策略联合决定；没有风险字段不是自动通过。拒绝缺字段、空对象、与 artifacts 不一致的 PASS；旧协议保守迁移，不猜测缺失数据。
- 本轮及全部分段的未解决 finding/request 必须合并；汇总轮不能删除、降低或遗忘它们。修复后由新 SHA 的证据明确闭合。

reviewer 仍只有 read/grep/find/ls。它提出验证需求，不执行 shell。宿主只执行项目已配置/固定发现的检查入口；需要新增探针时交编码 Agent 在授权任务内写入回归测试、提交后由宿主执行。绝不把模型返回的命令字符串直接交 shell，也不把裸 PR 当成允许执行代码的授权。

这保留 reviewer 的独立性，同时获得本次人工复审中“提出边界假设→实际运行→据证据判缺陷”的能力。

## 6. 预算、恢复和幂等

- 保留单任务唯一活跃 run、所有转换走 Store/run_events、scrubbed env、宿主发布和匹配 SHA 合并。
- 需求版本使用当前已批准的 Issue 内容哈希，不由 reviewer 声明。claim run/预留尝试、预算递增和活动 run 约束必须在同一 Store 事务中完成；崩溃、检查提前失败和已启动后取消不退还尝试。原 code run 内 FIXING 与 review 派生修复共享修复额度，不能通过沿用会话逃逸预算。
- 同一个任务需求版本共享自动修复预算，默认沿用 server.retry_limit；补测试也消耗该预算。新提交、分段或模型重试不重置额度。
- 同一个需求版本最多 3 个基础设施尝试轮次（首次 + 2 次恢复）；退避 30 秒、120 秒。进程内格式纠正仍最多 3 次调用，计入该轮总时限。自动恢复与修复预算分别统计，总任务最多 6 轮自动检查/评审轮次，先到任一上限就停止。
- 评审每轮默认 10 分钟总预算，包含所有分段、汇总和格式纠正，并受 server.max_task_minutes 更小值约束；已有检查继续使用其自己的配置时限。超过容量不会无限拆分/增时/更换模型碰运气。
- 持久化每轮 head_sha、base_sha、需求版本、policy_version、尝试类型与父轮次、已耗预算、next_attempt_at。服务重启不重置计数，也不启动可能仍存活的子进程。
- 执行错误记为 ERROR，不记作代码 high。ERROR 在有剩余预算且到期时可调度重试；不能再因为“此 SHA 已有任意 verdict 行”而永久卡住。PASS/BLOCK/人工决策结论不会因普通轮询自动重审。
- 外部人员提交新 HEAD 可触发一次新评审，但需求版本内预算不清零；无自动额度则继续停在受阻态。人工“继续”是有记录的预算续期，不删除历史证据。
- 自动修复、合并冲突修复、外部推送导致 HEAD 变化，均使旧批准失效。与现行“冲突修复继承 approved_sha/approved_by、不重评”的规则有意不同，实施时同步更新 AGENTS.md。
- 新版不自动重开旧 PR、不恢复暂缓/无需处理、不重放历史 AWAITING_HUMAN。用户可按当前版本申请重评；历史记录保留 policy_version=legacy。

## 7. 数据、API 与兼容

不新增业务相位。新增持久化评审控制信息和版本化证据：

- tasks.review_control_json：需求版本、预算计数、retry 时间、处理类型、当前待决策/待验证项、policy_version=2；通过 Store 事务读改写，状态版本与活动 run CAS。
- 每个通过宿主校验的 decision_request 由宿主分配稳定 request_id；重复评审的同一问题按需求版本、类型、影响范围和语义摘要识别，不用模型随机文本作为主键。持久化 question、type（product_choice / breaking_change / sensitive_authorization / configured_hold）、选项、影响路径、要求的具体权限与 head_sha。
- 决策回答也保存在 review_control_json 的追加式 resolutions 中，字段含 request_id、需求版本、head_sha、影响范围、所选方案/具体授权内容、操作者与时间。默认批准只绑定当前 SHA；任何新 HEAD 或需求变化使其失效，必须形成新的明确回答，不自动扩展成未来授权。实施首次版本不支持跨 SHA 的模糊授权。
- check_results.review_detail_json：协议 v2 的原始判定、宿主决策依据、证据引用及各分段结论；旧行保持 null，不回填假证据。
- next schema migration 仅新增上述可空列，旧策略结论继续可查看。可空列本身不能阻止历史二进制访问新库，因此受支持的降级仅为：排空停机、还原 v2 启用前的数据库/配置备份、启动配套旧代码；明确禁止旧二进制原地连接 v2 数据库。受管启动脚本校验数据库最低运行版本与代码版本，不匹配则拒绝启动；新版 CLI 同样核验。绕过启动脚本手动执行任意历史代码不属于受支持回滚，不能宣称可由新列阻止。
- GET /api/tasks 及详情增加 attention.kind：decision / approval / execution_error / recovery / advisory，并保留 summary/detail/next_step 兼容现有客户端。额外返回具体问题、来源和下次重试时间。
- 现有 rereview、approve-merge 继续要求鉴权、任务版本、PR/Issue 状态、人工锁和 SHA 核验。人工 approve-merge 不能跳过未完成检查、完整性失败或未闭合阻塞缺陷；它只解决批准/授权问题，变化后仍须通过技术门禁。
- 新增 POST /api/tasks/:id/decisions/:request_id/resolve，要求鉴权、expected_updated_at、decision_version、head_sha、selected_option 与明确授权内容。服务端核验 task source=issue、无活跃 run、问题仍有效、远端 HEAD/Issue/人工锁未变化；在与 stop/rereview/approve-merge 相同的任务互斥与 Store CAS 事务中追加回答。与远端复核之间状态改变则拒绝，不能落到其他 SHA。
- 此 API 只记录该问题的选择/授权，不立即合并；还有其他未回答问题时保持等待，全部解决后回 AWAITING_REVIEW，重新校验选择后的实现与技术门禁。外部删除/迁移的运行本身仍需独立执行授权，不包含在“允许合并某段代码”中。
- 普通 approve-merge 和 agent-merge 标签仅处理 merge approval，不能回答产品取舍、破坏性兼容、敏感授权或解除人工锁/保护路径。在存在此类问题时拒绝普通合并批准并提示具体 request_id；manual 模式需先回答具体问题再批准合并。
- driveMerge 在每次实际合并前独立复核 Issue OPEN、远端人工 hold/needs-human、任务版本及 policy_version、当前 HEAD/base 与证据一致、决策回答有效、检查通过、无未闭合 finding。网络未知则等待重试，Issue 关闭则归档，门禁新增则停在对应等待状态；直接添加 agent-merge 标签不能绕过这些检查。提交远端 merge 之前再次核对本地版本；远端合并继续使用 --match-head-commit，明确不声称能够将 GitHub 多次读取与 merge 原子化。
- 新评审协议 v2 输出验证失败走执行恢复，不能通过解析叙述抽取一个可能是示例的 PASS 来自动合并。

auto_merge.max_files/max_lines 在策略 v2 下只作为审查规划阈值，仍解析旧配置并在启动日志说明语义；不再作为最终合并硬门禁。代码风险核查替代旧 assessRisk 二值升级。项目新增可选 human_review_paths（默认空），匹配后产生显式配置门禁，不把匹配当成缺陷。

auto_merge.enabled、review_mode、pr_review 的授权语义不变。新策略以 review_policy.version: 2 显式启用；没有该项继续执行现行策略，部署不静默扩大自动合并范围。启用属于用户确认后的实施范围，无需逐 PR 再批准兼容增量改动。

## 8. 外部完成状态对账与界面

- 仅对本实例管理、没有活跃 run 的任务对账；外部 PR 合并沿用现有完成路径。
- Issue 已关闭但关联 PR 未合并/不存在，默认映射为 CANCELED（外部关闭），不是 COMPLETED；人工已暂缓/无需处理的处置不覆盖。关闭不等于代码完成，不基于评论猜测全部完成。
- #26 可归为“外部关闭（替代 PR 已落地）”，若无机器可验证的替代关系不自动认定本任务已合并；#82 无本机 PR，同样外部关闭归档，并保留维护者完成说明供查询。
- 关闭对账清掉 pending retry 与下一次自动重试，保留历史错误，避免持续提示“等待同步”。远端请求失败时保持本地状态，不把查不到等同于已关闭。
- 同一次事务检查最新任务版本、无活跃 run、人工处置；与 stop/重评互斥。重新打开外部 Issue 不自动恢复历史任务，需显式继续。
- “待我处理”分成“待你决策/合并批准”和“执行受阻”两种明确类别；顶部决策数量不计执行故障。保持现有入口，不扩充成需求管理产品。
- 决策卡片展示具体问题/选项/影响；故障卡片展示失败阶段、已尝试动作、证据链接与恢复入口；不统一加 agent-high-risk。

## 9. 当前案例的目标分流

| 案例 | 新策略 | 不能省略的步骤 |
|---|---|---|
| #39 并发 Promise.reject() 被吞 | 验证发现后自动 BLOCK→修复→回归→重评；无授权问题不找人 | 新增无拒绝原因异常用例；不能沿用旧 PASS |

## 11. 实施边界与设计审查

影响：types/config、Store migration/调度幂等、review prompt/parser、checks/修复闭环、merge preflight、UI attention 分类、文档及 AGENTS 不变量。复用现有 checks、pending_fix、单 run 约束、SHA 钉住、分段和生成物重建能力。

与现行契约的有意差异：不再把 reviewer high 和规模直接作为硬门禁；执行错误可预算内重试而不被同 SHA verdict 锁死；冲突修复新 HEAD 重新评审；人工批准不绕过技术门禁。实施必须同步修改测试、配置说明和 AGENTS.md，不能只改提示词。

阻塞确认项：无。用户已明确确认本设计 v1，进入实施。

审查记录：首轮 independent FAIL（1 High：具体决策回答和授权范围未闭合）；已补稳定请求 ID、持久化回答、独立 API 与 SHA 绑定。第 2 轮 independent 增量复审 PASS，确认授权闭环、与合并批准分离、最终门禁及关联预算/兼容边界无未解决 Critical/High。首轮覆盖全文及必要的 ops/engine/Store，第二轮覆盖修订的决策回答链路与受影响门禁。设计 PASS 不代表代码或运行时已经实现。
