# 设计与执行分离工作流约定

> 状态：生效的流程约定（2026-10-20）
> 来源：沉淀自 issue #2（分级模型策略）与 #4（设计约定），两者关闭后以本文档为权威来源。
> 关联：P0/P1/P2 审查闭环的具体实施项见 [pr-review-optimization-plan.md](./pr-review-optimization-plan.md)。

## 1. 原则

**强模型处理不确定性（设计、审查）；低成本模型处理明确、可验证的执行；确定性验证不使用 LLM；人保留关键决策权（设计审批、执行授权、合并 PR）。**

不以"所有阶段都用最强模型"为目标，也不假定设计完成后所有编码都适合低成本模型。

## 2. 模型分配（默认模板 / 建议基线，非硬性规定）

下表是**标准模板**：实际选择以各 Runner、Provider、网关与额度的验证结果为准，人工可按任务特征随时覆盖，复杂任务必须由人工显式指定。

| 阶段 | 默认模型 / 方式 | 说明 |
| --- | --- | --- |
| 需求澄清、方案讨论、架构设计 | `gpt-6.1-sol`（high） | 阅读代码与约束，比较方案与风险；未决问题不得伪装成已确认需求 |
| 设计审批 | 人工 | 未确认不得进入自动编码 |
| 创建/整理 Issue | 模板/程序优先 | 只把**已批准**设计转为结构化 Issue；创建 Issue ≠ 授权执行 |
| 常规编码与一般修复 | `deepseek-v4.1-flash` | 隔离 worktree 内修改，按验证证据修复 |
| 复杂/跨模块/高风险编码 | `gpt-6.1-sol`（high） | 人工显式指定，不让低成本模型反复无效试错 |
| 确定性验证 | 无 LLM | 受信测试/lint/typecheck/构建，记录命令、退出码与 HEAD SHA |
| 独立只读 Review | `gpt-6-luna`（high） | 隔离上下文，对照原设计验收标准检查；Review 不能替代测试 |
| 交付 | Draft PR + 人工合并 | 附检查证据、审查结论、已知风险；不自动合并 |

补充约束：

- 文档列出模型不代表当前 Runner 已验证可用，以实际 CLI、协议、网关、权限和思考参数透传为准。
- 不使用 Claude/Claude Code 系列模型；`glm-5.3-flash` 仅可作非关键整理类任务候选。
- 暂不扩展 Linear、Jira、禅道等外部任务适配器，沿用 GitHub Issues + SQLite 分工。
- 失败时按明确配置才可升级模型；升级保留原需求、测试证据与失败摘要，**不重置当前 run 的修复预算**，不得借升级自动新建 run 续杯。
- 记录每次运行的 Runner、模型、思考等级、Token/费用（取不到精确值记 UNKNOWN）、检查结果、修复轮数、最终 PR 状态，为将来是否实现自动模型路由提供依据。

## 3. Issue 可执行契约

由设计阶段产出的执行 Issue 至少包含：

- **目标及非目标**：解决什么，不处理什么；
- **背景和代码上下文**：相关模块/路径、现有约束、兼容性要求；
- **批准的实施方案**：关键设计决策与不可违反的限制；
- **验收标准**：可客观判断的行为、边界条件和失败行为；
- **验证要求**：必须执行的测试/命令及预期结果；
- **风险与回退方式**：数据迁移、权限、安全、并发等（适用时）；
- **任务复杂度与执行模型**：默认 `normal / deepseek-v4.1-flash`，复杂任务明确标记并由人工批准 `complex / gpt-6.1-sol`；
- **人工审批状态**：设计讨论稿、设计已确认、可执行授权分别区分；只有遵循仓库现有审批机制后才允许自动领取。

执行阶段禁止自行改变已批准的目标、接口契约、数据模型或架构决策；发现重大遗漏/冲突必须暂停回到设计讨论，而非在修复循环里反复猜测。

## 4. 执行与审查闭环边界

1. 首次执行按人工指定模型启动；常规任务默认 DeepSeek，复杂任务直接 GPT。
2. 失败先分型：确定性测试失败可在同一方案下有限修复；需求含糊/方案冲突返回设计审批；环境、权限、额度问题暂停并标出阻碍。
3. 修复与 Review BLOCK 共用**每个 run** 的自动修复预算（默认 3 次，不含首次实现）；恢复、模型升级不重置计数。
4. 任何代码修复后重新执行权威 checks，再独立 Review；测试/Review 证据必须对应最新 HEAD SHA。
5. Review 为独立只读会话，只对照设计检查偏离，不在 Review 环节篡改设计决策。
6. 预算耗尽或同类问题持续失败即停止转人工；只有人工确认原因并明确 Retry 才开启新 run。PR 只建 Draft，合并由人工完成。

## 5. 状态分层

- **GitHub Issue**：业务需求、设计结论、人工批准、验收标准、是否授权执行（权威来源）；
- **SQLite / Agent Control**：run 生命周期、执行阶段、模型选择、失败原因、修复次数、Token/费用、崩溃恢复状态；
- **PR / CI**：代码改动、检查结果、独立审查证据与最终人工合并。

不要用 GitHub 原生 open/closed 硬承载全部执行状态，也不让内部 run 状态越权代表业务审批。

## 6. 成本与验证

- 允许为 run 配置时间/Token/费用上限，切换模型不得绕开预算。
- 按真实样本比较"设计较充分 + 低成本执行"与"直接强模型编码"的整体成本、完成率和返工率——本策略是**待验证的工程假设**，不是已证明的节省比例。
